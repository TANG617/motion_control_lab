# Motion Control Lab 研究愿景

## 文档定位

本文面向参与机器人算法、运动控制和平台开发的团队成员，用于统一
Motion Control Lab 的建设目的、研究边界和长期方向。

本文是一份研究愿景，而不是单个实验的实施规格。具体实验的问题、变量、指标、
阈值和执行方式应在独立的实验定义与 README 中说明，不在本文中预先展开。

## 背景与核心目的

当前线上机器人运动控制链路以 C++ 和 ROS2 为基础，并使用 placo 作为 IK
求解器。随着业务场景增加，求解链路中逐步积累了更多 task、输入处理和下层规划
逻辑。它们对求解质量和运行效率的实际影响尚缺少统一、可复现的评估依据。

Motion Control Lab 的核心目的是：

> 基于真实遥操作数据建立可复现的离线 Benchmark，系统研究运动学
> whole-body IK 链路中的 task 配置、输入规划和关节空间规划，并为未来
> `motion_control_core` 重构或替换 placo 提供可信的 A/B 依据。

长期北极星是建设能够持续积累数据、复用实验输入和支撑算法准入的 Benchmark。
近期则首先用它解释并优化当前 placo 链路。

## 研究目标与成功图景

Motion Control Lab 希望逐步实现：

- 建立统一、版本化且能够持续扩充的遥操作动作 Benchmark；
- 在相同输入和受控条件下复现、分析与比较不同运动控制方案；
- 解释 task 配置、笛卡尔输入处理、IK 求解和关节空间规划分别如何影响精度、
  连续性、实时性与鲁棒性；
- 为当前 placo 优化提供证据，并为新的核心算法库或候选求解器建立一致的
  A/B 评价基础；
- 将未来真机闭环运行产生的 MCAP 数据回流到 Benchmark，持续补充真实业务
  场景和边界案例。

最终，团队应能够基于同一批可追溯输入回答“为什么修改”“修改带来了什么”
以及“候选方案是否值得进入下一阶段验证”，而不是依赖少量演示或主观观察。

## 研究边界

V1 聚焦运动学层面的 whole-body IK，以及 IK 输出之后的关节轨迹规划。这里的
whole-body IK 指由多个运动学 task 和约束共同决定关节解，不包含动态 WBC。

当前阶段暂不覆盖：

- 接触力与力分配；
- 逆动力学；
- 力矩控制；
- 其他需要完整动力学模型和闭环接触验证的问题。

当前证据主要来自真实数据的离线 MCAP 回放，因此离线实验只能支持对数值行为、
算法性能和候选方案差异的判断，不能直接证明真机运行效果得到改善。未来进入真机
闭环阶段后，真机数据仍以 MCAP 形式落盘并回流到本项目；涉及真机效果的结论必须
由相应的闭环验证支撑。

IK 输出与下层关节空间规划之间的影响关系暂时作为开放研究方向保留。其具体研究
对象、系统边界和变量将在建立对应实验时单独定义。

## 核心资产：遥操作动作 Benchmark

遥操作动作 Benchmark 是所有研究方向共享的基础资产，不属于某个 task 优化实验
的附带结果。

它由真实业务产生的原始 MCAP 数据构建。原始数据保持可追溯，在预处理阶段按照
明确的动作片段进行切分和标注，并转换为适合重复回放与分析的规范 CSV 数据。
Benchmark 应能够随新的业务场景、边界情况和真机闭环数据持续扩充，同时保持
版本可识别、输入可复用。

placo 或其他求解器生成的轨迹都是实验结果，而不是 Benchmark 中唯一正确的
“标准答案”。不同算法可能产生不同但同样有效的关节解，应根据统一研究目标进行
评价。

该 Benchmark 服务于算法研究和受控比较，不定位为线上业务使用的动作模板库。

## 研究方向

### 1. Task 必要性、冗余与冲突

**问题：** 为适配不同业务场景而加入的 placo task 中，哪些是必要约束，哪些存在
功能重叠、冗余计算或相互冲突？

**价值：** 解释 task 组合对求解行为和运行效率的影响，减少历史配置累积造成的
不透明性。

**预期决策：** 为不同动作和场景明确 task 的保留、合并、调整或移除方向，形成
后续优化当前 placo 链路的依据。

### 2. IK 输出与关节空间规划

**问题：** IK 求解结果的数值特征会如何影响下层关节空间规划，以及最终可执行
轨迹的表现？

**价值：** 建立 IK 与下层规划之间的因果边界，避免将链路下游的问题笼统归因于
IK 求解器。

**预期决策：** 在后续具体实验中明确问题来自 IK 输出、关节空间规划还是二者的
组合，并据此选择优化位置。本方向暂不预设具体算法或参数。

### 3. 笛卡尔空间输入规划

**问题：** 当遥操作输入的笛卡尔空间轨迹不够平滑时，在 IK 前加入规划或平滑处理，
能否改善关节空间输出，同时避免不可接受的延迟和操作意图偏差？

**价值：** 识别输入质量与 IK 输出质量之间的关系，避免仅通过下游补偿处理上游
问题。

**预期决策：** 判断哪些输入问题适合在 IK 前处理，以及该处理是否值得进入后续
闭环验证。

### 4. 核心算法库与求解器 A/B

**问题：** 当 `motion_control_core` 重构或业务准备移除 placo 依赖时，候选实现
能否在统一 Benchmark 上保持有效性，并具备满足业务需求的执行效率？

**价值：** 将库重构和求解器替换从接口迁移问题转化为有历史基线、统一输入和
可追溯结果的工程决策。

**预期决策：** 判断候选实现是否具备进入集成和真机验证阶段的条件。placo 是当前
生产基线，但不被视为唯一正确输出。

## 工程原则

- 算法实现和实验执行以 C++ 为主，数据分析与可视化以 Python 为主。
- Lab 应能在 macOS 上原生运行，不能把启动 ROS2 容器作为前置条件；核心算法
  执行不依赖 ROS2 graph 或 runtime，MCAP 解码与算法执行保持解耦。
- placo 以可追踪的源代码形式接入，而不是依赖不可追溯的预编译二进制。
- 原始 MCAP 数据保持原样，经过显式预处理后，以 CSV 作为主要的数值数据交换
  和分析格式。
- 实验数据和图表应由落盘数据生成；静态图表同时输出 PNG 和 SVG。
- CSV 不是所有元数据的唯一格式。运行状态、来源、配置和产物完整性等信息遵循
  实验架构中的相应合同。
